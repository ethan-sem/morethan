# M5-07 内部顾问数据维护手册

> 完成日期：2026-08-14  
> 流程版本：`CareerDataRelease 1.0.0`  
> 适用对象：MoreThan 求职顾问、数据复核顾问和发布负责人

## 1. 流程目标

本流程用于维护公司目标池、公开来源白名单和岗位族映射表，不建设账号、数据库或运营后台。所有操作在本地项目中完成，操作者姓名只作为发布留痕，不具备登录、权限认证或电子签名含义。

核心原则：

- 不直接编辑 `public/data/career-copilot` 中的已发布文件；
- 每次维护使用独立发布编号和草稿目录；
- 编辑者不得担任复核人；
- 必须有两位不同复核人完成同一版本复核；
- 复核后任何字节变化都会使发布失败；
- 发布前再次运行数据门禁和完整项目检查；
- 检查失败时恢复旧数据，不写“已发布”记录。

## 2. 角色分工

| 角色 | 责任 | 禁止事项 |
|---|---|---|
| 编辑顾问 | 创建草稿、核对来源、修改三份数据 | 不能复核自己的版本，不能直接覆盖生产数据 |
| 复核顾问甲 | 独立检查事实、日期、许可边界和产品口径 | 不能代替第二位复核人 |
| 复核顾问乙 | 再次独立检查，并确认与甲相同的数据哈希 | 不能与编辑者或复核甲同名 |
| 发布负责人 | 明确确认发布，查看完整检查结果 | 不能绕过双人复核、哈希或构建门禁 |

同一人可以在不同发布批次承担不同角色，但同一批次内编辑者、复核甲、复核乙必须为三位不同人员。

## 3. 标准操作

### 3.1 创建维护草稿

```powershell
pnpm run data:prepare -- --release=release-2026-08-20 --editor=张三
```

命令会把当前三份生产数据复制到：

```text
work/career-data/releases/release-2026-08-20/draft/
```

并生成 `release-manifest.json`，记录编辑者、验收日期和三份文件的 SHA-256。该目录为本地工作区，默认不进入 Git。

### 3.2 编辑草稿

只编辑本次 `draft` 中的文件：

- `company-role-pool.json`；
- `source-whitelist.json`；
- `role-family-map.json`。

修改后先手工打开所有相关官方页面，再更新日期。不得只延长到期日却不重新核验页面。

### 3.3 复核一

```powershell
pnpm run data:review -- --release=release-2026-08-20 --reviewer=李四 --confirm-all
```

### 3.4 复核二

```powershell
pnpm run data:review -- --release=release-2026-08-20 --reviewer=王五 --confirm-all
```

两次复核均会重新运行完整静态数据门禁，并记录当时文件哈希。`--confirm-all` 表示复核人已经逐项完成第 4 节清单；不是跳过检查的快捷开关。

### 3.5 发布

```powershell
pnpm run data:publish -- --release=release-2026-08-20 --publisher=赵六 --confirm-publish
```

发布命令依次执行：

1. 确认已有两位独立复核人；
2. 确认草稿哈希与复核时完全一致；
3. 按中国标准时间重新检查所有有效期；
4. 备份当前生产数据；
5. 复制已复核草稿到生产数据目录；
6. 运行 Lint、类型检查、全部测试、解析依赖探针、数据门禁和生产构建；
7. 成功后生成 `docs/career-copilot/MVP前端版/发布记录/<releaseId>.json`。

第 6 步失败时自动从本次备份恢复旧生产数据，不生成发布记录。

## 4. 六项复核清单

每位复核顾问必须独立确认：

1. `official_sources_opened`：实际打开了涉及变更的官方公开页面；
2. `facts_match_sources`：公司、方向、入口和日期与来源一致；
3. `dates_and_expiry_checked`：核验日期真实，到期日符合复核周期；
4. `no_live_vacancy_overclaim`：没有把招聘首页或目标池写成实时职位；
5. `no_tiers_scores_or_probabilities`：没有公司永久档次、排名、分数或录取概率；
6. `privacy_and_usage_policy_checked`：没有账号区、个人应聘信息、Cookie、批量抓取或未经许可的正文复制。

任一项无法确认时不要运行 `--confirm-all`，退回编辑顾问修订并重新开始两次复核。

## 5. 常见变更规则

### 5.1 只续期

即使 URL 未变化，也必须重新打开页面。更新来源、入口、记录和数据集的相应日期后，两位顾问重新复核。

### 5.2 新增公司

先将官方招聘入口加入白名单，再添加公司、来源、入口和目标记录。不得为了新增公司破坏 6 个方向的覆盖或引入第 31 家公司；MVP 固定规模变更需先调整产品任务范围。

### 5.3 新增细分岗位族

同时更新方向引用、相邻岗位引用、外部分类依据和顾问复核信息。MVP 当前固定 18 个，扩容需要单独产品任务。

### 5.4 来源不可访问或出现限制声明

不要继续延长日期。将来源降级、替换或加入排除项；如果目标记录失去合格来源，应移除或替换该记录，保持 30 家和方向覆盖门禁。

## 6. 发布记录与恢复

正式发布记录进入 `docs/.../发布记录/`，包含人员姓名、时间、检查清单、数据哈希和备份相对路径。记录不包含账号、联系方式、简历、Cookie 或密钥。

备份留在本地 `work/career-data/releases/<releaseId>/backups/`。如发布后发现内容问题，停止继续发布，使用备份比对并创建一个新的修复发布编号；不要修改已经生成的历史发布记录。

## 7. 验收标准

- 编辑发生在隔离草稿中；
- 三位角色独立；
- 两次完整清单复核；
- 复核后文件未变化；
- 发布前数据门禁和完整项目检查通过；
- 发布前旧数据已备份；
- 失败可自动恢复；
- 成功发布拥有不可变数据哈希和发布记录。
